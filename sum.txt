GrowthRadar — AI Growth Intelligence Platform for UserGuiding
Project Summary
================================================================================

CONTEXT
-------
Starting point: an empty project directory containing only Agents.md, which
defines engineering rules (prefer simple/modular/typed code, no unnecessary
dependencies, avoid hardcoded secrets, fail gracefully, ask before guessing,
explain trade-offs before major architectural decisions, prefer open-source/
local-first solutions).

GOAL
----
Build a platform that automatically identifies high-potential companies for
UserGuiding by analyzing their public websites: understand their product,
evaluate onboarding quality, detect opportunities, and produce a Lead Score
with clear reasoning — an intelligent product, not just a scraper.


ARCHITECTURAL DECISIONS MADE (and why)
---------------------------------------
Since the request was open-ended, these calls were made directly (per Agents.md
"think like a senior engineer") and documented in README.md rather than left
implicit. Some were revised after the initial build based on real-world testing
and explicit user direction — noted below where that happened.

1. Python, CLI-first, with a single reusable core function.
   `growthradar.core.pipeline.analyze_company(url)` is the one entry point every
   interface (CLI, Streamlit dashboard) calls — it returns both the LeadScoreResult
   and the underlying CompanyEvidence, so a caller can persist or display the raw
   collected data, not just the final score.

2. Facts vs. judgment are deliberately split.
   - Deterministic, rule-based code decides ICP fit (self-serve SaaS or not)
     and disqualifiers (e.g. already a UserGuiding customer) — these are
     factual questions, not opinions, so they're cheap, reproducible, and
     testable without any LLM call.
   - An LLM (or its offline stand-in) is reserved for genuinely subjective
     judgment: product complexity, onboarding gaps, and pitch framing — and
     even then its output is a fixed JSON schema validated by Pydantic, never
     a freehand final score.
   - The final Lead Score is a plain, auditable weighted sum of dimension
     scores, computed in code (scoring/scorer.py), not by the LLM.

3. Local-first LLM layer, with both a paid and a free upgrade path.
   `HeuristicProvider` is a fully offline, deterministic reasoning engine
   (rule-based, same structured output shape as a real LLM) used by default —
   the platform works with zero API keys, zero external calls, zero cost.
   Two real-LLM providers implement the same `LLMProvider` interface:
     - `AnthropicProvider` (Claude, model "claude-sonnet-5" by default) — used
       when `ANTHROPIC_API_KEY` is set.
     - `GroqProvider` (Llama 3.3 70B via Groq's free-tier-friendly, fast API) —
       added on user request as a no-cost alternative to Claude; used when
       `GROQ_API_KEY` is set and no Anthropic key is present.
   Auto-selection order is Claude > Groq > heuristic (first key found wins),
   overridable via `GROWTHRADAR_LLM_PROVIDER=anthropic|groq|heuristic`. If a
   live call fails mid-run, the pipeline logs a warning and falls back to the
   heuristic provider rather than crashing a batch job.

4. SQLite over Postgres.
   Zero setup, ships with the Python stdlib (no ORM dependency added), and an
   append-only `lead_scores` table preserves score history per domain over
   time. Swapping to Postgres later only touches storage/.
   REVISED: a `evidence_json` column was added (with an automatic migration
   for pre-existing databases) so the full collected evidence behind a score
   — not just the final numbers — can be retrieved and inspected later. This
   was an explicit user request: "ben istediğim zaman o veriyi alıp
   inceleyebileyim" (I want to be able to pull and inspect that data whenever
   I want). raw_html is stripped before storage; it's only needed transiently
   for tech detection during a run and would otherwise bloat the database.

5. Headless-browser fetching (Playwright) — REVISED from the original decision.
   Original build used `httpx` (plain HTTP GET) for speed and simplicity, with
   Playwright noted only as a documented future extension point for JS-heavy
   sites. The user later asked specifically for real browser-based fetching so
   client-side-rendered (React/Vue/Next.js) sites yield their actual content
   instead of an empty pre-render shell, and to use it for every site, not as
   an opt-in — so `httpx` was removed entirely rather than kept as an unused
   alternative (per explicit instruction not to keep anything unnecessary in
   the project). `collection/playwright_fetcher.py` is now the only fetcher.
   Implementation notes from getting this working:
     - Selenium was tried first, using a snap-packaged Chromium the user
       installed via `apt`. It failed with "cannot join mount namespace of pid
       1: Operation not permitted" — snap's confinement model is structurally
       incompatible with being launched by an automation driver in this sandboxed
       shell environment. This is not fixable via configuration.
     - Playwright was used instead, which downloads its own non-snap Chromium
       binary into the user's home directory (no snap confinement, no sudo
       needed for the browser itself). It initially failed with a missing
       shared library (`libnspr4.so`); running `playwright install-deps` (needs
       sudo, run once by the user in their own terminal) resolved this cleanly.
     - The default Playwright wait strategy (`wait_until="networkidle"`) was
       tried first and found to be impractically slow on real sites, because
       sites with continuous analytics/tracking requests (Mixpanel, PostHog,
       etc.) never go network-idle, so every page fetch stalled for the full
       timeout. Switched to `wait_until="domcontentloaded"` plus a fixed 500ms
       pause, which is fast (a full ~9-page site analysis dropped from
       2-3+ minutes to ~30 seconds) and still lets client-side JS render its
       content before the page is scraped.
   robots.txt is still checked before every fetch, a descriptive User-Agent is
   still sent, and a configurable crawl delay is still applied between requests.

6. Tech/tool detection via a local signature table (Wappalyzer-style),
   not a paid third-party API (BuiltWith/Wappalyzer). Keeps the platform free
   to run at any volume and fully offline-capable. Covers onboarding/adoption
   tools (UserGuiding itself, Appcues, Pendo, Userpilot, WalkMe, Chameleon,
   Userlane, Whatfix, Intro.js, Shepherd.js), chat/support widgets, analytics,
   help-center platforms, CRM/marketing tools, and payment processors.

7. Everything is environment-configurable (.env), nothing hardcoded that a
   growth team would reasonably want to tune: scoring weights, hot/warm
   thresholds, request timeout, max pages per company, crawl delay, DB path,
   log level, LLM provider/model.

8. Streamlit dashboard as a thin UI layer over the same pipeline function.
   Added on user request ("bir dashboard tarzi bir yer var mi... streamlit vb
   bir arayuz"). `growthradar/dashboard.py` calls the exact same
   `analyze_company()` / `storage.repository` functions the CLI uses — no
   parallel logic, no duplicated business rules. Shows the score, tier,
   per-dimension reasoning, and (per decision #4 above) a "Collected data (raw
   evidence)" section with the actual page text/detected tech/signals behind
   any score, for both a fresh analysis and any past one picked from history.


WHAT WAS BUILT — FILE BY FILE (current state)
-----------------------------------------------
growthradar/
  __init__.py               Package version marker.
  config.py                 Settings + ScoringWeights dataclasses; tiny built-in
                             .env loader (no python-dotenv dependency); every
                             field overridable via environment variable.
  cli.py                    argparse-based CLI: `analyze`, `batch`, `list`, `show`
                             subcommands; wires pipeline + storage + formatters.
  dashboard.py              Streamlit UI: analyze form, score/tier/reasoning
                             display, raw-evidence viewer, history table with
                             per-domain evidence inspection. Run with
                             `streamlit run growthradar/dashboard.py`.

  core/
    models.py                Pydantic models shared across every layer:
                              PageContent, DetectedTech, CompanySignals,
                              CompanyEvidence (+ evidence_bullets() for LLM
                              prompts), DimensionScore, LeadScoreResult, Tier enum.
    pipeline.py               analyze_company(): orchestrates evidence
                              collection -> ICP scoring -> disqualifier checks
                              -> LLM-assisted assessment (with fallback) ->
                              final scoring. Returns (LeadScoreResult,
                              CompanyEvidence). The platform's single entry point.

  collection/                (deterministic evidence gathering — no LLM here)
    playwright_fetcher.py     PlaywrightFetcher: fetches pages with a real
                              headless Chromium browser (domcontentloaded +
                              short fixed wait, not networkidle -- see decision
                              #5) so JS-rendered sites yield real content.
                              Never raises past itself -- fetch failures are
                              recorded on PageContent instead.
    page_discovery.py         normalize_base_url(); discover_candidate_urls()
                              finds same-domain pricing/about/careers/docs/blog/
                              changelog/customers pages from homepage links.
    extractor.py               parse_page() (title/meta/visible text via
                              BeautifulSoup); CTA detection (signup/trial/demo)
                              via regex; B2B vs B2C keyword lists;
                              estimate_pricing_tiers() heuristic.
    tech_signatures.py         Local signature table: tool name -> category ->
                              regex patterns. Extend by adding one entry.
    tech_detector.py           detect_technologies(): matches signatures against
                              combined page HTML, deduplicated.

  analysis/                  (facts -> judgment -> structured evidence)
    evidence_builder.py        build_evidence(): ties fetcher + discovery +
                              extractor + tech_detector + robots.txt together
                              into a validated CompanyEvidence object; applies
                              crawl delay between requests.
    icp.py                     score_icp_fit(): deterministic rule-based ICP
                              dimension (signup/trial CTAs, pricing tiers, B2B
                              vs B2C language, careers/blog presence, payment
                              processor detected, homepage reachability).
    disqualifiers.py           find_disqualifiers(): hard-exclusion rules
                              (existing UserGuiding customer; site unreachable
                              or robots-blocked with no evidence collected).

    llm/                       Pluggable qualitative reasoning layer.
      base.py                   LLMProvider abstract interface + LLMProviderError.
      schemas.py                LLMAssessment Pydantic model (the fixed contract
                              every provider must satisfy): product_experience
                              score+reasoning, onboarding_opportunity
                              score+reasoning, recommended_pitch_angle,
                              confidence.
      prompts.py                System prompt (UserGuiding growth-analyst
                              persona, strict JSON-only, "never invent facts")
                              + build_user_prompt() rendering CompanyEvidence
                              as bullet-point facts.
      anthropic_provider.py     Real reasoning via the Claude API (model
                              configurable, default claude-sonnet-5); guarded
                              import so the `anthropic` package is only required
                              if this provider is actually selected; parses and
                              validates the JSON response, raising
                              LLMProviderError on any failure (caught upstream).
      groq_provider.py          Same contract via Groq's OpenAI-compatible chat
                              API (default model llama-3.3-70b-versatile) --
                              a free-tier-friendly alternative to Claude, added
                              on user request. Guarded import, same JSON
                              extraction/validation/error-wrapping pattern as
                              AnthropicProvider.
      heuristic_provider.py     Fully offline, deterministic provider producing
                              the same LLMAssessment shape via transparent rules
                              (e.g. "no competitor onboarding tool detected +
                              self-serve trial + 3+ pricing tiers -> high
                              onboarding opportunity"); also builds the
                              recommended pitch angle. This is what makes the
                              whole platform runnable with zero external
                              dependencies or cost.

  scoring/
    scorer.py                  compute_lead_score(): weighted-sum combination of
                              dimension scores using configured weights;
                              disqualifiers cap the score at 15 and force tier
                              EXCLUDED; otherwise tiers into hot/warm/cold via
                              configurable thresholds. Pure, deterministic,
                              auditable — the one place "how much each
                              dimension counts" is decided.

  storage/
    db.py                      SQLite connection/schema management (stdlib
                              sqlite3, no ORM); creates lead_scores table with
                              a domain index on first use; _migrate() adds the
                              evidence_json column to pre-existing databases so
                              older on-disk DBs keep working.
    repository.py               save_result() (append-only, preserves history
                              per domain; optionally stores the CompanyEvidence
                              behind the score, with raw_html stripped),
                              list_results() (filter by tier),
                              get_latest_for_domain(),
                              get_evidence_for_domain() (retrieves the stored
                              evidence for a domain's latest run, for the
                              dashboard's raw-data viewer).

  reporting/
    formatters.py               to_json(), to_markdown(), to_table() renderers
                              for a LeadScoreResult; FORMATTERS registry used
                              by the CLI's --output flag.

  utils/
    logging.py                  configure_logging() — single basicConfig call,
                              level driven by settings/CLI flag.
    robots.py                   load_robots() / can_fetch(): fetches and parses
                              robots.txt with a timeout, defaults to allow-all
                              if unreachable (matches robotparser convention),
                              never raises.

tests/                        15 unit tests, no network access required:
  test_tech_detector.py        UserGuiding self-detection, competitor tool
                              detection, no false positives, deduplication.
  test_icp.py                  strong PLG/SaaS signals score high, consumer

  test_scorer.py                weighted-average math is correct, disqualifiers
                              cap score and force EXCLUDED tier.
  test_heuristic_provider.py    no-competitor-tool + self-serve scores high

  test_extractor.py             title/meta/text parsing strips scripts

  (These tests were unaffected by the fetcher swap or provider additions --

HOW TO EXTEND (documented in README.md)
-----------------------------------------
- New tool/tech to detect          -> one entry in collection/tech_signatures.py
- New scoring dimension            -> a function returning DimensionScore,
                                       wired into core/pipeline.py, weight added
                                       to config.py
- New LLM provider (e.g. Ollama)   -> implement LLMProvider.assess() in
                                       analysis/llm/, no other changes
- New storage backend (Postgres)   -> reimplement storage/repository.py against
                                       the same functions
- Web UI or HTTP API                -> call core.pipeline.analyze_company()
                                       directly; the Streamlit dashboard already
                                       does exactly this
- A lighter/faster fetcher for      -> PlaywrightFetcher is the only fetcher now;
  simple static sites (if needed       a plain-HTTP alternative could be added
  again later)                         back behind the same fetch()/close()/
                                       context-manager shape it exposes


STATE AT HANDOFF
-----------------
Fully working, tested, documented MVP, since extended with: a free (Groq) LLM
option, raw-evidence persistence + inspection (SQLite + Streamlit dashboard),
and headless-browser (Playwright) fetching for JS-rendered sites, replacing
the original plain-HTTP fetcher entirely per explicit user instruction to keep
the project free of anything no longer needed.

No git repository has been initialized (user has not requested one).
Chromium (via Playwright) and its system dependencies are installed on this

sandboxed shell cannot prompt for sudo passwords itself). The Streamlit
dashboard runs at http://localhost:8501 via `streamlit run growthradar/dashboard.py`.


NASIL ÇALIŞIYOR — TÜRKÇE ÖZET (GÜNCEL AKIŞ)
================================================================================
Kullanıcı bir domain verdiğinde (CLI'den `growthradar analyze linear.app` ya da
Streamlit dashboard'dan) sırayla şunlar olur:

1. Adres normalize edilir, robots.txt kontrol edilir (izin yoksa hiç
   taramadan durulur).
2. Ana sayfa ve ondan keşfedilen ~8 anlamlı sayfa (pricing, about, careers,
   docs, blog, changelog, customers) gerçek bir headless Chromium tarayıcısı
   (Playwright) ile çekilir -- bu sayede JavaScript ile render edilen (React/
   Vue/Next.js gibi) siteler de doğru şekilde okunur, sadece boş bir HTML
   iskeleti değil.
3. Her sayfadan başlık/metin/CTA (kayıt ol, ücretsiz dene, demo) çıkarılır,
   fiyatlandırma katmanı sayısı tahmin edilir, B2B/B2C dil ağırlığı ölçülür.
4. Sayfaların HTML'i, yerel bir imza tablosuyla (regex) ~35 araç için taranır:
   UserGuiding'in kendisi mi var (zaten müşteri), rakip bir onboarding aracı
   mı (Appcues, Pendo, vb. -- displacement fırsatı), yoksa hiçbiri mi
   (boş alan fırsatı)?
5. Bu kanıtlardan (CompanyEvidence) deterministik ICP Fit puanı ve
   diskalifiye kontrolleri hesaplanır -- bunlar gerçek, LLM'e sorulmaz.
6. Kanıtlar bir LLM sağlayıcısına gönderilir (ürün deneyimi + onboarding
   fırsatı değerlendirmesi + satış pitch'i için): API key yoksa yerel/offline
   HeuristicProvider, ANTHROPIC_API_KEY varsa Claude, o yoksa GROQ_API_KEY
   varsa Groq (Llama 3.3 70B, ücretsiz) kullanılır. Canlı çağrı başarısız
   olursa otomatik olarak Heuristic'e düşülür.
7. Üç boyut (ICP Fit, Ürün Deneyimi, Onboarding Fırsatı) sabit ağırlıklarla
   (düz Python kodu, LLM değil) tek bir 0-100 puana indirgenir; diskalifiye
   varsa puan 15'in üstüne çıkamaz ve tier=EXCLUDED olur, yoksa HOT/WARM/COLD
   eşiklerine göre etiketlenir.
8. Sonuç (skor, tier, gerekçe, pitch) ve altındaki ham kanıt verisi (her
   sayfanın metni, tespit edilen teknolojiler, sinyaller) birlikte SQLite'a
   kaydedilir -- geçmiş hiç silinmez.
9. CLI'de tablo/JSON/Markdown olarak, Streamlit dashboard'da ise skor kartı +
   gerekçe + "Collected data (raw evidence)" bölümüyle (geçmişteki herhangi
   bir analiz için de) gösterilir.

Katman mantığı özetle:
  Toplama (Collection)  -> sadece GERÇEK: tarayıcıyla HTML çek, metin çıkar,
                            teknoloji tespit et
  Analiz (Analysis)     -> GERÇEK'ten KURAL'a: ICP puanı, diskalifiyeler (LLM yok)
                         -> GERÇEK'ten YORUM'a: LLM/Heuristic ile ürün &
                            onboarding değerlendirmesi
  Skorlama (Scoring)    -> YORUM'ları sabit ağırlıklarla tek puana indirger
                            (yine LLM yok)
  Depolama & Rapor      -> sonucu VE ham kanıtı saklar, okunabilir formatta
                            ve dashboard'da gösterir

Bu ayrım sayesinde sistem hem açıklanabilir (her puanın nereden geldiği
gösteriliyor, ham veri istendiğinde incelenebiliyor) hem tutarlı (kural bazlı
kısımlar her seferinde aynı sonucu verir) hem de genişletilebilir (yeni bir
araç tespiti, yeni bir puanlama boyutu, yeni bir LLM sağlayıcısı eklemek tek
bir dosyaya dokunmak demek).
